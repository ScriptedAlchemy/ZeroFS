# Raw-device storage increment

The target gives ZeroFS two whole HDDs for payload and one whole P3 for the journal, catalog, authority, key envelopes, scratch and clean cache. The original Storage data disk stays in its existing TrueNAS pool. The boot disk and Storage disk are outside the ZeroFS device set.

The engine pool uses the raw object store and region adapters in `zerofs/raw-device`. The small Linux fixture uses bounded loops on private tmpfs inodes. The larger fixture uses independently claimed, fully allocated ext4 backing files. ZeroFS issues positioned I/O on the loop block devices in both cases. The candidate also implements a separate physical claim for three fixed designations. The package previously qualified on the small raw fixture used an adapter and a 1.5 GiB companion allowance. [Physical claim and larger geometry](raw-device-physical.md)

## Device and acknowledgement contract

The fixture verifies the kernel's backing device and inode against a separately opened descriptor, the whole block-node identity, capacity and mount/holder state. It retains the backing inode lock and the block claim during I/O. Reopen also requires matching pool UUID, logical member UUID, region role and geometry. The physical claim resolves the designated by-id alias through the initial Linux host namespace, checks kernel and udev identity and topology, and compares the held descriptor before and after inventory inspection. Its fixture and hardware entry points have distinct arguments.

Explicit HDD initialization requires zero bytes in both label slots and the first log block. It refuses a valid ZeroFS label in either slot. P3 initialization checks the whole device for zero bytes before writing its first role. Every P3 open validates all six region bindings. An interrupted multi-region initialization requires offline inspection if any role is incomplete. Ordinary startup only opens existing labels.

### Format v1 baseline at `cca24f5e`

- Label slots at offsets 0 and 4096 held pool/member IDs, role, geometry, provisioning nonce, generation, `durable_tail`, record count and checksum. After them, each PUT or DELETE appended a 4 KiB header containing the nonce, contiguous sequence, operation, key, payload size and digest. A PUT followed its header with block-rounded payload. [Label and record layout](https://github.com/ScriptedAlchemy/ZeroFS/blob/cca24f5e/zerofs/raw-device/src/format.rs#L1-L64)
- Open replayed records from block 2 up to `durable_tail`, checking every header against its required sequence and the nonce. PUT and DELETE updated the in-memory index immediately. FLUSH synced the records before writing and syncing each label in order. Open ignored records beyond the chosen checkpoint. Physical free bytes were the suffix past the append cursor. [Replay](https://github.com/ScriptedAlchemy/ZeroFS/blob/cca24f5e/zerofs/raw-device/src/store.rs#L206-L259) · [Mutations and FLUSH](https://github.com/ScriptedAlchemy/ZeroFS/blob/cca24f5e/zerofs/raw-device/src/store.rs#L262-L359) · [Space reporting](https://github.com/ScriptedAlchemy/ZeroFS/blob/cca24f5e/zerofs/raw-device/src/store.rs#L461-L469)
- The member adapter charged a rounded PUT plus one future 4 KiB tombstone per live key above the physical reserve. The catalog added the physical overhead of pending uploads to their logical quota before placement and evacuation. The filesystem GC already writes packs of live frames and deletes dead segments through the pool. Pool evacuation durably verifies and publishes a destination before retiring the source. ### Format v2 allocation and commit

The layout is two 4 KiB labels, then two equal index banks, then the data area. Each bank occupies `round_up_4KiB(max(min(size / 32, 16 MiB), size / 4096))`. The index contains keys, physical locations and object metadata. A data allocation owns `ceil(length / 4096)` payload blocks and at least one map block, with another map block for each additional 502 payload blocks. A contiguous allocation encodes its block range directly. A fragmented allocation stores a linked, checksummed map of its ordered payload block addresses. The fixed allowance makes PUT cost independent of fragmentation. DELETE needs only index space. [Format](../zerofs/raw-device/src/format.rs) · [Allocation](../zerofs/raw-device/src/store/allocation.rs)

PUT writes into free blocks and stages the new index entry. DELETE stages removal. FLUSH appends checksummed mutation pages to the current bank or writes a packed snapshot of just the live index to the other bank. The live index budget ensures a snapshot always fits. The flush syncs payload, maps and index before writing and syncing label 0, then label 1. Both labels store the selected bank, its birth generation, committed byte tail, and last sequence. Pages must match the provisioning nonce, bank generation and exact offset. Open walks only this committed prefix, then claims blocks for the final live entries and rejects overlaps. Historic index records never read payloads or maps. Unpublished pages and stale data bytes have no authority on reopen. [Index encoding](../zerofs/raw-device/src/store/index_log.rs) · [Flush and reopen](../zerofs/raw-device/src/store.rs)

When FLUSH returns, both labels reference the new index, so either can survive a torn or lost peer. Before that point the writer leaves the old index prefix and old payload intact. Once both labels advance, overwritten and deleted blocks become reusable after any open read handles release them. If a crash left just one valid or newer label, the first subsequent write repairs and syncs the other label before writing any payload or index bytes. This prevents reuse while the older checkpoint can still be selected. A crash before publication keeps the previous state. A crash after one complete label write can expose the synced new state. Scratch map pages bind to the nonce, object sequence and ordinal, and all reachable pages are written in full before publication. These guarantees depend on the device honoring its flush contract.

The allocator consumes any free 4 KiB blocks, so aggregate free bytes above reserve can fund a new payload even across disjoint holes. A replacement still needs space for its new allocation until the commit. The pool reserves the exact allocation cost and continues to track catalog cleanup debt. The raw member's preallocated index banks cover tombstones, so segment retirement now restores usable physical capacity. The same path handles reserved metadata keys and repeated publication and retirement of generations.

V1 object regions are explicitly refused. V2 requires fresh media. The bounded HDD blank check and the binding checks still run. The separate P3 transactional journal and catalog region formats retain their own labels. The standalone landing probe still verifies the destination before retiring its durable pending object.

### Memory and qualification

The allocator has one bit per 4 KiB data block, at most 30.52 MB per decimal TB. The live index charges 192 bytes plus key length against the lesser of half a bank and `max(8 MiB, size / 25,600)`. At HDD scale this budgets 39.06 MB per TB for live entries. An unflushed retirement keeps a 32-byte allocation descriptor and can retire at most the preceding committed index's cardinality. Vector growth budgets up to another 13.03 MB per TB. For 18 TB this gives about 1.49 GB total for the bitmap, live index budget and unflushed retirements, plus up to 4,096 pending keys, per-operation mapping/verification buffers and explicitly pinned reader allocations. The index can fill before the data area when objects are small or keys are long. A 90-byte key, for example, needs roughly 7.2 MB average payload to use 18 TB within the index budget. Full-scale saturation, latency after fragmentation or index rollover, and physical power-loss qualification remain open.

## Engine integration

| Role | Current engine implementation | Remaining work for physical use |
| --- | --- | --- |
| HDD payload | Pool locators bind the pool and member UUIDs. Raw segment PUT enforces conditional creation and updates, checks the exact copy-on-write allocation cost, and flushes before returning. A range read verifies the entire object in bounded chunks. Mounted FUSE evidence covers one file spanning two members and continued allocation when the smaller member reaches reserve. | Qualify reuse and evacuation at hardware scale and measure independent physical HDD drains. |
| P3 journal | The v2 journal region backs the production writeback redb transactions. The same durable commit publishes the payload chunks, mutation records and local progress. Remote retirement releases allocator pages. An explicit resize ceiling fences the physical reserve. | Qualify full-capacity operation, long-lived readers, target-device power loss and endurance. Until drain, the P3 holds the only durable copy of an acknowledged write. |
| P3 catalog | A separate redb region holds placement, reservations and locators. Ordinary startup requires an existing catalog identity. | Prove restoration or replica recovery after P3 loss. |
| P3 metadata and keys | The authority store holds the SlateDB objects. The key-envelope path routes to its own store on the same P3. Both retain an exclusive device claim. | Exercise rotation and restore a usable namespace after P3 loss. |
| P3 scratch and clean cache | Both regions have fixed boundaries. The candidate leaves them unused and runs the clean cache in RAM. The fixture uses private temporary directories for sockets, control files and the mount. | Persistent hot-read retention and scratch allocation/reclamation on raw media. |
| Loss and identity | Mounted reads returned EIO on the affected file after live media loss. The unaffected file remained readable. Offline migration moved a live segment and verified its destination hash. Cold startup requires both HDDs by default. Operators can opt into startup with one confirmed absent HDD. | Hardware qualification of the physical claim and its host exclusions. |
| Clients and admission | The original small synthetic profile admits one exact geometry in a dedicated 8–16 GiB Linux cgroup with zero swap, the package WebUI feature and a provisional 1 GiB companion allowance. | Combined acceptance on the larger candidate with the actual package, transfer rates, and hardware FLUSH/FUA on the raw path. |

The original small synthetic fixture uses a 96 MiB journal, 32 MiB catalog, 88 MiB metadata, 8 MiB keys, 16 MiB scratch and 16 MiB clean-cache layout for this fixture. Object-store and transactional regions have different labels. Opening an incompatible region fails. All-device blank verification applies to initialization of either format. A quick wipe does not establish that the device passes that check.

The fixture manifest selects 16 MiB and 128 operations of volatile filesystem writes, 16 MiB of writeback RAM, and a 16 MiB dirty journal budget. A segment rotates after a complete write batch: a maximum negotiated 9P write can add almost 10 MiB to an open segment holding almost 4 MiB. The writeback RAM budget covers that complete segment and its framing so it can reach the journal and satisfy fsync. The admission calculation charges two volatile ownership stages, open and retained segments, clean-cache floors, raw index and replay memory, and companion headroom. It resolves to 7,876,902,912 bytes (7,512 MiB). The 1 GiB companion allowance is provisional. [Exact manifest](../zerofs/src/cli/memory_raw_fixture.toml) · [Raw HDD mounted evidence](evidence/raw-mounted-members/README.md)

The historical mounted receipts used the earlier 8 MiB writeback RAM budget and smaller fixture writes. They do not cover a maximum-size negotiated 9P write; the current budget corrects that gap without changing the historical measurements.

## Reproduction

Run `scripts/test-raw-device.sh` on Studio Docker Desktop. It builds the locked standalone crate, runs the unit tests, then starts a separate network-isolated container with loop control and access to block major 7. Owned mappings use Linux autoclear and their backing inode is checked at teardown. The only ext4 volume is a disposable negative control for signature and mounted-device refusal. [Measured results and cleanup](evidence/raw-device-engine/README.md)

Run `scripts/test-raw-device-mounted.sh --degraded-start BIN_DIR` to exercise
cold startup with one absent member. Supply the Linux `zerofs` and
`zerofs-raw-device` executables in `BIN_DIR`. The fixture uses a 44 GiB
cgroup limit and checks the default refusal, byte-exact survivor reads, the
affected paths and their I/O errors, and all three files after the missing
member returns.

The upstream SPDK Blobstore at the package's SPDK revision is a separate raw-block allocator with blob IDs, asynchronous I/O channels and metadata synchronization. Its metadata operations use the SPDK thread that loaded the store. Reusing it for payload reclamation remains an option. That integration would need a Rust-to-SPDK service boundary or FFI, exclusive claim transfer, a durable object-key-to-blob index, data-barrier verification and measured memory/CPU admission. This draft uses the positioned-I/O log for the bounded device proof.
