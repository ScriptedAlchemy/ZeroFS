# Explicit memory budget diagnosis and design

## Scope and evidence

This design describes a proposed explicit memory budget for ZeroFS. Source inspection supports the design, but it does not establish a safe production memory envelope.

The source inventory refers to `origin/main` at `90baaac12280e1a61fa6932e6788666c79337dc8`. Line references identify that revision. NFS dependency references identify `0c19924faa3b09041d198d167785a7de80ea48b5`. Foyer and redb references identify `foyer-storage 0.22.3` and `redb 4.1.0`.

A previous startup rejection on a different baseline reported a requirement of 40.12 GiB for an 8 GiB envelope. It rejected that envelope before creating storage. That receipt establishes an admission rejection, not an RSS measurement or a deployment recommendation.

The operator selected a 4 GiB total budget as the target to qualify on November 16, 2026. The operator will cap ZFS ARC at deployment. Four GiB remains an unmeasured target. Step 1 adds planning and accounting types while retaining the legacy startup policy. The explicit budget cannot enable a bounded production mode until the later allocation and recovery work passes qualification.

## Step 1 implementation boundary

The shared `memory` library module exposes a pure planner, an injected-file detector, byte and entry leases, and one serialized `ResolvedMemoryPlan` receipt. The planner requires named working-set requirements and requested maxima for every pool. Future implementation steps must derive those inputs from enabled protocols and dependency geometry. A successful unit fixture does not qualify any backend.

The planner funds all minimum requirements first. It divides the remaining bytes by caller-supplied integer weights and caps each extra share at its requested maximum. Rounding and unused shares become headroom. Explicit dirty maxima must be minimum requirements. Clean capacity can be zero. Every plan reserves separate progress capacity and unallocated headroom. Pool capacities sum exactly to the selected budget.

The configuration loader parses `[memory]`, but server startup refuses that section until production enforcement is complete. Legacy configurations keep their existing startup policy and fixed reserves. The server resolves shared filesystem write acknowledgement before admission and passes that same resolved value into filesystem initialization. Planning charges the raw-input and accepted-overlay stages separately. Matching legacy aliases do not create extra stages.

The byte parser accepts an unsigned integer and an explicit unit. It supports B, KiB, MiB, GiB, TiB, kB, MB, GB, and TB. Fractions resolve against actual observations and round downward without converting the detected byte count to floating point. Missing sources remain unavailable observations. Host capacity can come only from a readable MemTotal field, and swap never adds capacity.

Acquire multiple ordinary pools in their declared order before taking filesystem locks. Each lease reserves bytes and one entry. Waiting records have a separate count limit. A `Bytes` owner retains its lease through clones and slices. Callers must acquire backing capacity before allocating and include container overhead in their requirements. These types do not yet account for production allocations.

- Not verified: Cgroup behavior under a real limit, production memory bounds, and the 4 GiB target remain unqualified.

## The five main findings

1. Startup adds 32 GiB for previously observed unmodeled residency and 8 GiB for process and companion overhead. These are admission reserves. The calculation does not allocate or touch those 40 GiB. Reducing those constants would remove a rejection without bounding the allocations that motivated it.
2. The configured clean-cache and dirty-RAM budgets are partial payload limits. They omit Foyer disk-engine buffers and indexes, a default 1 GiB redb page cache, segment buffers, protocol copies, and other state. Cache capacity, allocator residency, process RSS, and cgroup usage are different quantities.
3. Several paths have no useful memory byte bound. The commit queue and its batch drain are unbounded. SlateDB's memtable size limits are effectively disabled for seal-order correctness. The replication tail and replication decoder have no service-sized cap. NBD has no global connection bound.
4. Startup charges the legacy NBD volatile setting, although serving later resolves the shared filesystem setting. The shared volatile write path also has separate raw-input and accepted-overlay gates. A correct plan must use the resolved setting once and account for both ownership stages and their possible coexistence.
5. The NAS snapshot had 30,574,760 kB total RAM, no swap, 1,393,584 kB available RAM, and an ARC size of 26,541,061,392 bytes. Socket permissions denied access to Docker statistics. That snapshot cannot establish a new ZeroFS allocation or Plex's peak needs.

## What the existing reservations mean

A reservation is permission to consume bytes later. It is not evidence that those bytes are resident. A `Vec::with_capacity` reserves allocator storage but need not fault every page until use. A filled buffer does touch pages. A cache's weighted payload capacity excludes some keys, bookkeeping, references held by readers, serialization buffers, and allocator overhead. Eviction does not release memory while another owner still retains the backing allocation.

The tables distinguish the largest payload or configured charge visible in source from a worst-case resident bound. Where the full resident maximum is unknown or there is no service-level bound, the table says so. None of the payload sums below is a proven process RSS ceiling.

Use bytes for accounting. Existing `*_gb` values use decimal GB. GiB and MiB here use powers of 1024.

The source does not prove that all the unmodeled paths caused the previous OOM. The prior parts-slice retention bug is documented and the inspected warm path now copies each part. The remaining inventory still prevents a finite total resident claim.

## Proposed bounded budget

### One operator budget and one resolved plan

Add one `[memory]` section with exactly one budget selector. The following configuration illustrates the operator-selected qualification target. It is not a measured or enabled production envelope.

```toml
[memory]
total = "4 GiB"
```

An alternative is an explicit fraction, with no `total` alongside it.

```toml
[memory]
fraction_of_limit = 0.125
```

Parse byte quantities with checked integer arithmetic. Validate the fraction as finite and greater than zero and at most one, then round the result downward. A missing selector is a configuration error for the new bounded mode. Do not silently pick a host fraction. Fractional mode requires an available detected limit. An explicit `total` remains an operator declaration if detection is unavailable, and the receipt must state that its relationship to physical capacity could not be checked.

`B` is the total ZeroFS service target, including an explicit allowance for runtime and kernel charges. It is not the clean-cache size. Resolve all protocol endpoints, backend pools, read-only mode, writeback, shared write-ack settings, legacy aliases, and replication role before producing one immutable `ResolvedMemoryPlan`. Use that plan for constructors and the startup receipt. Do not recompute shares independently in cache, NBD, and SFTP code.

Legacy per-component sizes become requested maxima within `B`. Explicit dirty capacities are contractual maxima and must either fit the plan or cause a diagnostic rejection. Defaults may resolve to smaller derived capacities before service starts. Clean-cache requests are soft maxima and may shrink to zero, with the resolved values reported. Conflicting `[runtime] memory_limit_gb` and `[memory]` declarations should be rejected during migration instead of introducing a second hidden budget. A legacy declaration may be translated once if there is no ambiguity, with its source reported.

The planning invariant is that runtime capacity plus all live-allocation pools plus headroom is at most `B`. The runtime invariant is that each pool's owned charge is at most its capacity. Count queue slots and objects as well as bytes. A zero-byte payload still consumes metadata and an operation slot. No map, task registry, queue, retry list, dependency cache, or worker pool may bypass that invariant in a supported bounded configuration.

### How the budget is divided

The planner must first calculate the enabled configuration's irreducible working set. That includes the largest supported atomic request, its simultaneous decode and transformation allocations, one progress path through journal and metadata flush, fixed runtime workers, and any enabled replication message. It must reject a budget below that minimum and identify which requirement does not fit. Remaining bytes can fund caches, additional lanes, larger segments, and queued work.

The following 4 GiB division is a starting design example for qualification. Its sizes are proposed quotas, not measured resident needs. The planner must validate each quota against the selected backend and dependency implementations before accepting it.

| Pool | Example capacity | What it pays for and what happens at its boundary |
| --- | --- | --- |
| Runtime and fixed state | 256 MiB | This covers an explicitly capped thread and task baseline, allocator metadata, and fixed service state. Worker counts and blocking jobs are derived or capped. If the selected implementation's baseline does not fit, startup refuses it. |
| Metadata and replay | 512 MiB | This covers commit producers and batches, memtables, journal indexes, handle state, and correctness-required replay state. A possible subdivision is 256 MiB for memtables, 64 MiB for queued commits, 96 MiB for durable journal indexes, 64 MiB for replay, and 32 MiB for handles. Byte and entry admission block new work before state creation. A durable index can page to disk. |
| Dirty payloads | 768 MiB | This covers all open and sealed segment backing allocations and object writeback payloads. A possible subdivision gives 512 MiB to segments and 256 MiB to writeback. This example has no volatile overlay. Optional volatile mode must carve out its raw and accepted ownership stages from the same total or fail planning. |
| Protocol work | 512 MiB | This covers receive, decode, backend handoff copies, possible replies, and active connections across all enabled protocols and listeners. The actual number of simultaneous requests and sessions is derived from this quota. Readers stop before consuming bodies when credits are unavailable. |
| I/O, maintenance, and progress | 512 MiB | This covers journal write scratch, remote streams, transport packet queues, compaction, replay, and reserved control work. Allocate a protected progress subset before background work or foreground admission can use the rest. Reduce concurrency and chunk sizes when the selected geometry does not fit. |
| Clean caches and their engines | 512 MiB | This covers all clean payload caches, their keys and nodes, engine queues, engine pools, and disk indexes. The example cannot allocate 512 MiB of payload and then add engine costs afterward. Clean fills use immediate admission and may be skipped. |
| Unallocated resident and cgroup headroom | 1,024 MiB | This is capacity left unused by ordinary allocations for bounded kernel charges, allocator slack, and observation delay. It is not allocated at startup and cannot excuse an unbounded consumer. Its adequacy requires measurement under the selected runtime, filesystem, and container. |
| Total | 4,096 MiB | These reservations sum exactly to `B`. |

These proportions are a proposed starting policy, not new universal constants. The implementation should derive minima from enabled features and dependency geometry, then allocate remaining capacity by documented shares. A larger configured cache or more upload lanes must compete for the same remaining bytes. SSD tier capacity is not a second memory allowance.

A strict bound on application-owned live allocations is achievable with accounting and finite algorithms. An exact equality between those charges and RSS is not. The implementation must retain a distinct kernel and allocator allowance, observe actual residency and cgroup use, and qualify that allowance. It must not advertise a hard RSS proof while a dependency's storage or allocator growth remains unknown. An enabled feature without a finite allocation strategy is unsupported in the bounded mode until it is changed, rather than being covered by a renamed reserve.

### Charge allocation ownership before memory is touched

Introduce a process-wide `MemoryBudget` with byte pools, operation slots, bounded waiters, and move-only leases. Charge the capacity of the backing allocation, including reserved capacity and known container overhead, before allocating or growing it. Bound variable key and path sizes. Map capacity growth must reserve the replacement table's transient allocation before rehashing. Fixed allocation counts should have calculated upper bounds, rather than relying on a vague overhead multiplier.

A shared `Bytes` allocation must keep its charge until its final owner releases it. Passing a clone from protocol decode to a dirty tier does not create new physical payload and should transfer or share its lease. Creating a second copy requires a second reservation before copying. A slice that retains a larger backing buffer keeps the backing buffer's full charge. Do not release charge merely because an entry leaves a cache or a socket reply is cancelled.

An already allocated caller payload cannot become invisible while it waits for a downstream tier. The permit must travel with the payload across the full pipeline. If a third-party API cannot carry this ownership, wrap it with a bounded, pre-reserved input or change that dependency. A weighted cache alone cannot implement this lifetime rule.

Use one declared acquisition order. Prefer one combined working-set reservation at protocol or internal-job ingress when multiple simultaneous allocations are required. Keep blocking admission outside inode locks, append locks, metadata write permits, and the flush barrier. The existing synchronous commit enqueue relies on order under the inode lock. Preserve it by obtaining a commit reservation before taking that lock, then making enqueue consume the reservation without waiting. Do not turn `submit_owned` into a blocking send while holding the lock.

Queued messages and waiting producers must both be bounded. A bounded channel whose senders retain unrestricted transactions is insufficient. Cap the producers before constructing transactions, and cap batch bytes and records while draining the queue. Bounded waiter records need their own slot reservation. Cancellation before acceptance refunds all reservations. Cancellation after acceptance transfers ownership to the worker that must settle the operation.

### Bound dirty data and preserve the durability barriers

Open-segment geometry becomes a result of the memory plan. The current four lanes and segment-size defaults are throughput preferences. The plan derives how many lanes, how much capacity per lane, how many retained seals, and how much finalization scratch can coexist. Reserve a whole admitted append or split the operation into bounded internal pieces before claiming offsets. Include directory growth, compression output bounds, encryption overhead, and the simultaneous original and transformed representations. A seal threshold is not itself an allocation bound.

Keep separate active-upload and retained-seal ownership as the existing code does. A failed seal retains its lease until it is durably transferred or successfully retried. Reserving the replacement open buffer must not depend on evicting the failed seal. If the next generation cannot fit, stop new appends and use the protected flush path.

The writeback RAM limit remains independent of the clean cache. Retain its payload lease through journal staging and through any reader still referencing the payload. Release or transfer it only when the actual backing memory is no longer required. Bound multipart metadata and part counts, including zero-length parts. Derive journal queue depth, publication batch size, local concurrency, upload concurrency, and remote chunk fanout from their charged working sets. Large first records must use a separately budgeted path rather than bypassing a batch cap.

SlateDB must continue to publish metadata only through the seal barrier. Add a bounded write wrapper that reserves memtable and commit growth before mutation. Trigger a coordinator-owned seal and metadata flush before the memtable allowance is exhausted. Keep memory for the flush's frozen tables, builders, buffers, and output publication available while the active table still exists. Release table charges only after the flush no longer retains them. A limit on key/value lengths alone is insufficient if the dependency retains snapshots or old versions. Add dependency hooks or a bounded wrapper for those lifetimes where needed. Do not enable the currently disabled automatic SlateDB size flush as a shortcut.

Index memory must not grow with the entire SSD backlog. Store persistent journal indexes on disk with an explicit redb cache quota. Recover in bounded pages and retain only a bounded hot index, loading older state as needed. If a required live metadata set cannot fit and cannot yet page, fail startup with that reason while preserving the journal. Never delete acknowledged records to make startup pass. This is required for recovery into a smaller budget, as well as for steady-state operation.

Pressure changes when work is admitted, not the meaning of an acknowledgement. Ordinary buffered writes retain their existing durability level. SSD and remote receipts still require their existing cutoffs and exact publication rules. Flush, fsync, COMMIT, FUA, sync writes, and HA guarantees must not return earlier because memory is full. Accepted dirty payloads, pending metadata, and required replay results are never discarded to lower residency. Dirty limits may shrink only after natural drain, never below retained ownership.

RAM-only acceptance cannot guarantee survival of a process OOM kill. This follows from the existing volatile contract, including the explicit warning at `zerofs/src/cli/server.rs:1478` and buffered-write semantics at `zerofs/src/config.rs:1032`. The design preserves that contract and does not relabel RAM as durable. The recovery test must prove retention of dirty data that crossed the promised durable barrier. If the operator requires every returned write acknowledgement to survive a process kill, select an existing durable acknowledgement mode or implement a separately specified durable landing before acknowledging. A memory budget cannot supply that guarantee.

### Bound protocols, replication, and background work

Derive one shared protocol allowance across 9P TCP, Unix sockets, WebSockets, NFS listeners, NBD, and any administrative endpoint that reads or returns large bodies. Reserve connection state before spawning a handler. Validate a small header first, then reserve the full required working set before receiving its body. Hold reply ownership through actual socket transmission or terminal disposal. Bound slow and idle clients with session limits and existing protocol deadlines. Reserve a small control path so a flush can enter while writes are blocked.

The new mode can keep 9P's current request and receive pools, but their capacities must come from the resolved plan. NFS needs an injected limits and shared-admission API in the pinned dependency. Include its decode and VFS copies instead of charging only wire bytes. NBD must charge a 128 MiB request as 128 MiB plus its simultaneous scratch, or stream within a fixed admitted window while preserving operation ordering. Its current 64 MiB charge clamp must not survive in the new accounting. A request that can never fit must fail before side effects, rather than wait forever.

Fids, open files, locks, replay identities, and authentication or directory state need entry and byte limits. Refuse new handles or mutations before accepting them when their required correctness state cannot fit. Existing handles remain valid. Canonical dedup results must stay available for their promised retry period. Admit their retention cost with the original operation, and apply rate backpressure when that allowance fills. Do not shorten that retry promise under pressure. Clean metadata caches and best-effort replay caches may evict only under their existing semantics.

Give the replication tail both byte and batch limits. Set a finite encoded and decoded message limit that fits its assigned working set. Reserve receiver space before decoding or retaining a ship, or implement a bounded streaming admission exchange if the RPC library would otherwise allocate first. Account for the leader's encoded request and the follower's decoded copy. A transaction larger than the message allowance needs a deliberately atomic bounded transfer protocol or must be rejected before mutation. Arbitrary message splitting cannot weaken transaction or lineage semantics.

A full tail returns a distinct retryable admission result or delays credit. The leader can flush an existing prefix to shared durable storage through its reserved progress path, advertise that durable prefix, and retry after pruning. Preserve ordering, dedup lineage, and existing peer-copy acknowledgements. The leader must not treat memory exhaustion as permission to switch to a weaker acknowledgement or drop a retained tail. If a durable spool is chosen later, acknowledge its real durability and retain its disk and memory ownership explicitly.

SFTP packet and SSH channel queues need bounded byte ownership in addition to session and operation counts. Cap per-operation fanout and configure dependency buffers explicitly. Include the remote scheduler's next prefetched chunk and verification responses in the upload working set. Preserve the Storage Box account connection limit across all pools. Pool storage configurations must aggregate quotas across members. Generic object-store adapters that collect an entire unbounded response need streaming or a maximum-size admission check. Until a backend's buffering is bounded, refuse that backend in the new mode with a precise diagnostic.

All clean caches, including redb's page cache, parts, block, extent, tail, inode, directory, blob, and SFTP metadata caches, come from the same resolved clean allowance or an explicitly assigned metadata share. Account for disk-engine pools and indexes before payload capacity. Cap clean engine enqueue with an actual byte reservation, and skip insertion if it does not fit. If an engine cannot enforce the required memory limit, disable its optional clean disk tier or use a bounded replacement. Startup must not load a huge recovered clean-cache index first and check it against the budget afterward. Estimate or page it, or prune only owned clean cache before opening it.

Stop speculative prefetch and warm copying before their first allocation when an immediate clean or scratch lease is unavailable. Continue an admitted demand read using its reserved buffer even if caching is skipped. Eviction can lower clean target capacity, but releases global bytes only when the backing allocation is no longer referenced.

Make GC scans and journal recovery incremental. Cap candidates, dead-segment batches, deadline storage, listings, compaction input and output buffers, and concurrent blocking jobs. Persist required deadlines or revisit bounded ranges instead of collecting every dead segment in RAM. Coalesce bounded reclaim notifications by inode or durable cursor. Deferring clean cache work and optional compaction is allowed. Never defer away the only flush operation that can release dirty memory.

The upload and download commands need their own application of `[memory]` when colocated. Derive effective jobs and connection fanout from that client's budget, and report requested and effective jobs. Replace full-tree planning with a bounded paged plan or an owned disk spool if it must support arbitrarily many files. A standalone client on another machine consumes no server RSS, but its requests are still subject to server admission. A client inside the same cgroup must receive a separate declared share under the common service ceiling.

### Make progress possible at full capacity

Reserve progress memory at startup for at least one complete supported drain operation. That operation includes sealing a dirty generation, writing or publishing its journal or remote object as required, flushing corresponding metadata, processing the completion, and freeing ownership. Keep its I/O and control slots unavailable to new foreground requests and optional maintenance. Prove its worst-case requirement for each enabled backend. Do not assume that an empty clean cache will always release enough memory.

The full-capacity path is as follows.

1. New input waits before its body allocation, transaction construction, or irreversible mutation.
2. Optional fills and speculative work stop. Clean entries can evict under their normal semantics.
3. The reserved worker advances already accepted work across its existing durability boundary.
4. Completed backing allocations release their leases, and bounded FIFO admission resumes.

A writer must not hold the flush barrier while waiting for capacity that only a flush can release. A remote outage or full SSD may leave producers blocked for a long time. That is bounded backpressure. Existing protocol deadlines and terminal-error behavior still apply, and no success receipt may cover work that failed admission.

## Detect and assert the envelope

### Detection rules

Read `/proc/self/cgroup` and `/proc/self/mountinfo` to resolve the actual cgroup v2 mount and current path. Retain the existing handling for mount roots, private namespaces, escaped paths, and ancestor traversal. Read both `memory.max` and `memory.high` for the current cgroup and every visible ancestor. Record each path, value, role, and read status. The token `max` means no finite limit. Zero is a finite value and cannot become unlimited by accident. Reject malformed numeric values, overflow, and contradictory limits with their exact source.

Inspect every matching mount and readable alias. A nested bind may expose the current cgroup while hiding a tighter ancestor that remains visible through a broader mount. Do not let selecting that bind drop the ancestor from admission. The legacy startup detector shares this mapping and checks every visible hard ceiling as well.

Treat finite `memory.max` as a kernel hard ceiling. Treat finite `memory.high` as an operational pressure threshold, not an OOM or dedicated-capacity guarantee. A shared ancestor constrains the service but does not grant its remaining capacity to ZeroFS. Do not add ancestor limits or use a shared parent's entire budget as dedicated space.

Parse Linux `/proc/meminfo` `MemTotal` as kB times 1024 with overflow checks. Host MemTotal is the fallback detected capacity when there is no finite cgroup limit. It is always a physical ceiling, not proof of currently available RAM. If finite cgroup limits exist, compare with host capacity when readable and keep the tighter applicable ceiling. `MemAvailable` is diagnostic context and must not become a moving startup budget. Report swap separately. The no-swap NAS receives no swap credit.

For a fractional selector, use the tightest available finite cgroup hard ceiling and operational high threshold, constrained by readable host MemTotal. If there is no finite cgroup limit, use host MemTotal. Mark whether the basis is dedicated, shared, or host-wide. On a shared or host-wide basis the operator's explicit fraction is the allocation decision; do not imply exclusive ownership. An explicit byte budget must fit the visible ceilings and the planner's progress minima. Reject a requested budget above a finite applicable `memory.high`, with a diagnostic that this is an operational policy check rather than the kernel's hard limit.

If cgroup files are absent, unsupported, permission denied, or hidden, record that exact reason and attempt host MemTotal. A failure to read one source does not justify assuming it is unlimited. If host capacity also cannot be read, report `detected_limit = unavailable` with a reason for each failed source. Fraction mode must refuse to resolve. An explicit byte selector can still enforce application quotas, but the receipt must say that physical and kernel-envelope validation is unavailable. It must not invent a host size, a default fraction, or zero use. Detector fixtures use injected data. Run every test in Linux containers. Linux cgroup semantics require separate tests under real limits.

### Runtime observations and assertions

Export separate values for configured target, detected hard ceiling, operational high threshold, each pool's capacity, owned bytes, reserved future bytes, queue and waiter counts, skipped fills, admission wait duration, and required progress reserve. Include the source of every limit and the resolved volatile mode, backend geometry, and effective worker or session counts in the startup receipt.

Observe Linux process RSS through `/proc/self/status` or equivalent, allocator allocated and resident statistics, and the service's cgroup `memory.current`, `memory.stat`, `memory.events`, and available pressure data. Cgroup usage includes descendants and charged file or kernel memory. Process RSS and jemalloc resident must not be added together, and host ARC must not be added to a process's RSS. Report `anon`, `file`, socket, and relevant kernel categories separately when the kernel exposes them. Report stale samples and unavailable values with reasons. Never replace unavailable observations with zero.

Assert ownership accounting on every acquire, transfer, and release. Publish both logical dirty bytes and charged backing capacity so a mismatch can be diagnosed. A cache payload counter cannot certify a resident budget. Sampled resident and cgroup pressure provide a second brake. They stop new optional work and new foreground admission before the protected progress allowance is consumed. Hysteresis prevents oscillation. They do not cancel accepted dirty work or alter acknowledgement targets.

Watch for cgroup limit changes. If the effective limit falls below retained ownership, stop new admission, drain through the protected path, and report that the new envelope cannot currently be satisfied. Do not drop data or claim that the old headroom can withstand an arbitrary external reduction. On a shared parent, other workloads can still cause an OOM. A service-level hard cgroup limit and measured host coexistence remain necessary deployment controls for the NAS.

Startup must refuse an invalid or ambiguous selector, arithmetic overflow, impossible per-request working sets, explicit dirty maxima that do not fit, insufficient flush or replay memory, a budget above applicable visible limits, and any enabled path without a finite supported allocation strategy. It must also refuse to serve if existing required journal or replay state cannot be recovered within the budget. It must preserve that state and report the failed requirement. A bounded recovery-only drain can precede serving if implemented and verified. No rejection should create backend storage or alter authoritative data merely to test feasibility.

## Deployment qualification target

The operator selected an initial 4 GiB total ZeroFS budget for qualification. The operator will cap ZFS ARC at deployment. Peak TrueNAS, ARC, Plex, and other application needs still require measurement before this target can become a deployment envelope.

Four GiB is about 13.7 percent of the reported 29.16 GiB MemTotal. It would leave about 25.16 GiB for the rest of the host. The historical snapshot did not have four GiB available, and ARC's maximum was about 28.16 GiB. This analysis did not measure reclaim latency, the minimum healthy ARC, or host behavior during Plex transcoding. On a machine without swap, the design cannot assume that immediate reclaim frees memory for ZeroFS.

The proposed first envelope should be revisited using these unknowns.

| Workload | What remains unknown and must be measured |
| --- | --- |
| TrueNAS and kernel | Peak non-ARC memory, kernel and network allocations, middleware activity, app-management activity, and operational headroom during ordinary maintenance remain unknown. A single `free` snapshot cannot separate them. |
| ZFS ARC | The minimum ARC that preserves the operator's workload, current ARC minimum and effective tuning, pinned or unreclaimable parts, reclaim latency under demand, and the cost of reads during ARC reduction remain unknown. The measured `c_max` is a maximum, not an entitlement that can coexist with every other service. |
| Plex | Idle memory, peak concurrent streams, software or hardware transcode memory, scans, and any RAM-backed transcode storage remain unknown. Docker access did not permit per-container observation. |
| Other apps and client commands | Per-container limits and peaks, any colocated ZeroFS upload client, existing transfers, and shared-parent cgroup pressure remain unknown. This analysis did not inspect or change any transfer process or its state. |
| ZeroFS | Baseline and peak resident use under the proposed quotas, backend buffer amplification, journal recovery requirements, and the protected flush allowance need isolated qualification. Source-derived quotas are not measurements. |

The host admission calculation must compare a proposed ZeroFS target with measured coexistence needs and an agreed host margin. Do not subtract ARC from host used memory and then also count ARC as a separate allocation without understanding the accounting. The `free` fields and ARC's byte count are overlapping views, not disjoint components to sum. This design does not authorize changes to host, ARC, Docker, or application settings.

Test reductions that still leave the proven progress allowance. Do not promise survival when an external controller reduces the hard limit below existing resident requirements. |

The ordinary pressure test must have no OOM kill. The forced-OOM test deliberately violates that condition to test durable recovery. Keep their receipts distinct. Recovery of journaled dirty data does not retroactively make RAM-only acknowledgements durable.

Every fixture must shut down workers and remove only its exact owned containers, volumes, temporary journals, plan spools, and files. Verify that those paths are absent before declaring the test complete. Qualification must inventory every retained artifact and verify removal of owned fixtures.

## Smallest ordered implementation sequence

Each commit should include its focused unit or fixture coverage. Keep the old startup admission policy in force until every enabled allocation path in the new bounded mode has a plan. Merely adding the new configuration and removing the fixed reserves in the first commit would be unsafe.

1. Add the shared budget types, pure planner, and limit detector. Resolve filesystem write-ack settings before memory planning. Implement byte and entry leases, bounded waiters, checked arithmetic, explicit unavailable observations, and one receipt format. Parse the proposed `[memory]` selector and expose planning to tests. Do not enable a partially bounded production mode. This commit is verifiable with Linux container unit fixtures for detection, configuration normalization, accounting, and ownership lifetimes. The old server path remains available and unchanged in its admission policy.
2. Bound dirty and metadata ownership through the write pipeline. Reserve producer and commit capacity before lock acquisition, bound commit batching and memtables without bypassing the seal barrier, derive open and sealed segment geometry, and charge writeback journal staging and flush scratch. Set an explicit redb cache limit, page recovery and overlay indexes, and reserve dedup and replay metadata before acceptance. Preserve the current acknowledgement contracts and accepted-work ownership. This commit is verifiable with stalled-sink, cancellation, integrity, barrier-order, and bounded-recovery fixtures in Linux containers. Do not yet advertise the whole service as bounded.
3. Bring every clean cache and background job into the plan. Include Foyer engines and indexes, standalone metadata caches, prefetch scratch, blob caches, journal reads, and compaction. Replace full dead-segment and recovery collections with bounded processing. Bound blocking jobs and reserve the control and drain subset. This commit is verifiable by filling each pool, skipping clean work before copies, and completing a flush with foreground pools full. Unsupported dependency behaviors must remain an explicit reason the new mode cannot start.
4. Add configurable NFS admission in the pinned dependency and update its pin. Inject shared byte and connection budgets across listeners, including decode and reply lifetimes. Preserve the dependency's record, fragment, timeout, and durability behavior. This commit is verifiable with the dependency's bounded-stream fixtures and ZeroFS compile-time API integration when the implementation owner has the build slot. It supplies a finite API that the next commit consumes; it does not require a NAS deployment.
5. Connect network, replication, and client accounting. Derive 9P and NBD budgets, remove the NBD undercharge, cap sessions and persistent handles, bound SFTP packet and operation memory, bound replication decode and retained tails, and give colocated transfer clients a bounded plan and effective job count. Validate other enabled adapters or refuse them in the new mode. This commit is verifiable with protocol-stream fixtures, full-tail progress, slow-reader tests, and client buffer and spool cleanup. A plan cannot pass while an enabled adapter has an unknown allocation strategy.
6. Activate the explicit budget only after end-to-end coverage passes. Replace the 32 GiB and 8 GiB reserve admission with the complete resolved-plan check, wire live cgroup and resident observation, add the Linux container and OOM recovery suite, and document the startup receipt and operator sizing question. The verifiable state is a bounded configuration that accepts a fitting real container envelope, backpressures at full capacity without OOM, preserves promised durability through a forced-OOM restart, and removes its fixtures. Until those checks pass, describe the design and partial implementation as not production-ready.

A dependency change may require its own upstream review, but its API should be specified and tested before ZeroFS enables the new mode. The final activation commit must enumerate supported backends and refuse unqualified combinations. This sequence replaces hidden allocation growth and incomplete accounting. It does not treat lower constants as the fix.

## Open questions and verification limits

- The operator selected the 4 GiB qualification target. Its adequacy still depends on peak TrueNAS, capped ARC, Plex, and other application needs.
- The intended production protocol set, backend or pool members, replication role, write-ack mode, and colocated transfer clients determine the minimum viable working set. Their desired maxima need to be part of the implementation's input configuration.
- Dependency work must establish finite allocation strategies for SlateDB table and snapshot lifetimes, Foyer disk indexes and queues, NFS copies, and native SFTP buffers. Exact resident amplification is not known from these source reads.
- The operator's required crash guarantee must distinguish ordinary buffered acknowledgements from completed durable barriers. Survival of every RAM-only acknowledgement through OOM is not possible without a different durable landing contract.
- The production cgroup hierarchy, effective `memory.max` and `memory.high`, per-container limits, Plex peaks, and ARC reclaim behavior remain unknown. The single snapshot does not resolve them.
- Not verified: Source inspection and step 1 unit fixtures do not prove that any proposed envelope starts, stays within its resident allowance, avoids OOM, meets throughput requirements, or recovers dirty data. The tests under real cgroup limits and the integrity checks remain proposed qualification work.
- Not verified: The historical approximately 28.6 GiB excess residency was read from a source comment. This task did not reproduce that OOM or establish which present allocation paths account for those bytes.
